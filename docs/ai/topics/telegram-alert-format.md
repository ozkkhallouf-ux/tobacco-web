# تنسيق تنبيهات تيليغرام الموحّد (ozk_remind_bot)

طلب المالك (2026-10-14): تنبيهات واضحة على شاشات الهواتف، عربية RTL بأرقام إنجليزية
وأسماء أصناف مختلطة، بلا تداخل نصوص، بطاقة لكل صنف، وتقسيم الرسائل الطويلة دون قطع
بيانات أي صنف — **دون تغيير أي حساب أو أولوية أو حد تنبيه**.

## مسار الإرسال (كما هو، لم يتغيّر)

```
مصدر الرسالة ← notify_telegram(event, text, dedupe_key, minutes[, reply_markup])
            ← telegram_outbox (left(text, 3900))
            ← dispatch_telegram_outbox() كل دقيقة ← sendMessage {chat_id, text[, reply_markup]}
```

`dispatch_telegram_outbox()` لا يرسل `parse_mode` (`supabase/telegram-notifications.sql`،
والنسخة الحية في `supabase/migrations/20260914121528_telegram_delivery_confirmation_retry.sql`).
كل التنبيهات اليوم **نص عادي**.

## القرار: نص عادي آمن، لا HTML parse_mode

| | HTML parse_mode | نص عادي + عزل الاتجاه (المعتمد) |
|---|---|---|
| تغيير الإنتاج | عمود/وسيط جديد في `telegram_outbox` وتعديل الموزّع ⇒ هجرة على الإنتاج | لا شيء خارج الدوال/السكربتات المعنية |
| القصّ عند 3900 | قد يقصّ وسماً من منتصفه ⇒ تيليغرام يرفض الرسالة كاملة (تنبيه حرج يضيع) | القصّ يُبقي نصاً مقروءاً |
| أحرف `< > &` في الأسماء | تهريب إلزامي لكل قيمة ديناميكية، ونسيان واحد = رسالة مرفوضة | تظهر حرفياً ولا تُفسَّر |

تيليغرام يقبل النص بلا تفسير حين يغيب `parse_mode`، فلا خطر حقن تنسيق. الوضوح يأتي من
البنية (عنوان، سطر لكل حقل، فواصل، إيموجي الحالة) لا من الخط العريض.

## المنسِّق: `src/telegram-format.js`

منطق نقي (IIFE ← `globalThis.ozkTelegramFormat`)، ونسخته
`supabase/functions/_shared/telegram-format.js` مطابقة بايتاً ببايت.

| الدالة | العمل |
|---|---|
| `line(text)` | يبدأ السطر بـRLM (U+200F) ⇒ اتجاهه من اليمين ولو بدأ باسم لاتيني |
| `field(label, value)` | `RLM + "التسمية: القيمة"` |
| `name(value, fallback = "—", maxChars = 120)` | اسم ديناميكي داخل FSI…PDI (U+2068/U+2069) بعد `clean`؛ `maxChars` أطول للعناوين (فحص الصحة 300) |
| `num(value, digits)` | أرقام إنجليزية بفواصل آلاف داخل LRI…PDI (U+2066/U+2069) ⇒ `-5` لا تنقلب `5-`. التقريب **بعيداً عن الصفر عند النصف وبالتمثيل العشري** (منذ المرحلة A): `-2.25 ⇒ -2.3` و`1.005 ⇒ 1.01`، مطابقاً لـ`round()` على `numeric` في Postgres |
| `money(value, currency = "$", digits = 2)` | الرقم معزولاً ثم الرمز بعده: `1,234.5 $` و`-350,000 ل.س`. `USD`/`SYP` تُحوَّل إلى `$`/`ل.س`، وأي رمز آخر يُنظَّف ويُعرض كما هو |
| `time(value, {withZone, dateOnly})` | بتوقيت `Asia/Damascus`: `2026-10-14 23:00 (دمشق)`، والتاريخ داخل LRI…PDI وإلا انقلب إلى «23:00 2026-10-14». القيمة غير الصالحة `—` |
| `severity(level)` | `🔴 حرج` · `🟠 عالٍ` · `🟡 متوسط` · `🔵 منخفض` · `🟢 سليم` · `ℹ️ معلومة`؛ يقبل المفتاح (`critical`) أو التسمية العربية (`حرج`)، والمجهول نص منظّف بلا رمز |
| `clean(value)` | يحذف محارف التحكم والاتجاه الواردة (RLO/LRE/RLM/العزل) والأسطر، ويقصّ عند 120 محرفاً بـ`…` |
| `composeMessages({title, intro, blocks, footer, maxChars})` | يجمع الكتل في رسائل ≤ 3500، **لا يشطر كتلة**، يرقّم `(1/3)` عند التعدد، المقدمة في الأولى والخاتمة في الأخيرة |
| `stripBidi(text)` | للفحوص والمعاينة فقط |

الروابط **لا تُعزل**: توضع في آخر سطرها كي يتعرّف عليها تيليغرام كاملة قابلة للنقر.

حدود: `maxMessageChars = 3500` (وحدات UTF-16) تحت قصّ `notify_telegram` (3900 محرف) وحد
تيليغرام (4096). كتلة أكبر من الحد وحدها (غير ممكنة مع أسماء مقصوصة عند 120) تُرسل
منفردة مقصوصة بعلامة `…` بدل أن يرفضها تيليغرام. القصّ بأسطر كاملة، وإن لم يتسع حتى السطر
الأول قُصّ بنقاط الترميز بعد حذف محارف العزل، فلا يبقى LRI بلا PDI ولا نصف زوج بديل.

## ما طُبّق في هذه المرحلة

### 1) تنبيه النفاد حسب أولوية المبيعات (`src/stock-alert-priority.js`)

التصنيف كما هو حرفياً في `classifyItem`: 🔴 **نافد** = الرصيد ≤ 0، و🟠 **قريب من النفاد** =
يكفي ≤ `lowCoverageDays` (3) أيام أو الرصيد ≤ `low_stock_threshold`. الترتيب بالأولوية كما
هو. منع التكرار (`dedupeKey` من بصمة الأصناف وحالاتها) لم يتغيّر.

```
⚠️ أصناف مهمة قاربت النفاد (1/2)
العدد: 40 من 40 صنفاً مهماً
🔴 نافد: 20  ·  🟠 قريب: 20
الترتيب حسب الأولوية (صافي مبيع آخر 30 يوماً)
┈┈┈┈┈┈┈┈┈┈┈┈
🔴 Marlboro Gold 20s
الحالة: نافد
الأولوية: 1 من 40
الرصيد: 0 كروز
يعادل: 0 كرتونة
يكفي: 0 يوم
┈┈┈┈┈┈┈┈┈┈┈┈
🟠 ونستون أزرق — 100mm
...
```

سطر «يعادل» يظهر فقط حين `unit2Factor > 1`؛ وبدونه الرصيد بخانة عشرية. رسالة التقادم
بالبنية نفسها (`⏳ تنبيهات النفاد متوقفة` ← السبب ← سطر لكل مصدر ← فاصل ← الخاتمة).

المستهلكون الثلاثة يحمّلون المنسِّق قبل المحرك: `scripts/stock-priority-alerts.mjs`،
`supabase/functions/stock-priority-alert/index.ts`، `scripts/telegram-alert-samples.mjs`.
غيابه يرمي `telegram_format_unavailable` (يسجّله مراقب pg_cron فشلاً) بدل رسالة بتنسيق آخر.

### 2) تنبيه فشل GitHub Actions (`.github/workflows/alert-on-automation-failure.yml`) — المرحلة A

bash بلا منسِّق JS؛ `jq` يحاكي قواعد المنسِّق (`clean`، RLM، FSI/LRI…PDI) ويبني المحارف الخفية
من `\u` فلا يعتمد على locale الـrunner. النتيجة معرّبة (`failure` ⇒ فشل، `timed_out` ⇒ تجاوز
المهلة، `cancelled` ⇒ أُلغي، `startup_failure` ⇒ تعذّر بدء التشغيل، `action_required` ⇒ ينتظر
إجراءً يدوياً، `neutral`، `stale`)، والمجهولة تُعرض معزولة كما هي. إن تعذّر `jq` يُرسل النص البسيط
بالمعلومات ذاتها بدل إسقاط التنبيه. المفتاح `gha-fail:<اسم سير العمل الخام>` والنافذة 60 دقيقة كما هما.

```
🚨 فشل أتمتة
الوقت: 2026-10-14 23:00 (دمشق)
المنصة: GitHub Actions
┈┈┈┈┈┈┈┈┈┈┈┈
سير العمل: Deploy TOBACCO Web
النتيجة: تجاوز المهلة
الفرع: main
المحاولة: 2
الرابط: https://github.com/…/actions/runs/…
```

### 3) فحص صحة الموقع (`scripts/health-check.mjs`) — المرحلة A

`buildHealthTelegramMessage(problem, issueUrl, now)` بالمنسِّق نفسه: المعلومات التي كانت تُرسل
(المشكلة، الخطورة، الرابط) + سطر الوقت؛ الخطورة برمزها. عنوان المشكلة معزول ومقصوص عند 300.
`telegramDedupeKey` ونوع الحدث `health_check` ونافذة 180 دقيقة لم تتغيّر. تعذّر التنسيق يُرسل نصاً
احتياطياً بدل إسقاط التنبيه.

```
🩺 مشكلة اكتشفتها المراقبة الآلية
الوقت: 2026-10-14 23:00 (دمشق)
الخطورة: 🔴 حرج
┈┈┈┈┈┈┈┈┈┈┈┈
المشكلة: الموقع لا يستجيب (https://ozktobacco.com/)
الرابط: https://github.com/…/issues/…
```

### 4) غياب الزبائن المهمين `CUSTOMER_INACTIVE_5D` (`src/customer-intelligence.js`) — المرحلة B

`buildInactivityAlert` يبني النص بالمنسِّق نفسه؛ الحسابات (من «المهم»، الغياب ≥ 5 أيام، الترتيب)
وحدود الأجزاء (كل 20 زبوناً) ومفاتيح الرسائل (`CUSTOMER_INACTIVE_5D:<يوم المرجع>:<بصمة زبائن الجزء>`)
ومفاتيح الحالة (`customer_inactivity_alerts`) ونافذة 1440 دقيقة **كما هي حرفياً** — تكافؤ 3000 حالة
مصطنعة مع النسخة السابقة بلا فرق إلا النص. بطاقة لكل زبون بثلاثة أسطر: الاسم (معزول ومقصوص عند 40
حرفاً كي تبقى رسالة الـ20 زبوناً تحت 3500 حرف في أسوأ حالة: 3,483)، ثم الغياب وتاريخ آخر فاتورة
`YYYY-MM-DD` معزولاً، ثم الفجوة المعتادة والشراء الشهري بعملته (`$` أو `ل.س`، لأقرب عدد صحيح).
تمييز العدد العربي: يوم واحد، يومان، 3–10 أيام، وما فوقها يوماً. العدد في الجزء الأول وحده.
المنسِّق مطلوب لبناء الرسالة فقط (`telegram_format_unavailable` صريح عند غيابه)؛ الواجهة التي
تحمّل المحرك بلا منسِّق لا تتأثر. الدالة الطرفية `customer-inactivity-alert` تستورد
`../_shared/telegram-format.js` قبل المحرك.

```
🔕 زبائن مهمون بلا شراء منذ 5 أيام أو أكثر
العدد: 3 زبائن · الأهم أولاً
┈┈┈┈┈┈┈┈┈┈┈┈
1. محل النجمة للتجارة
الغياب: 12 يوماً · آخر فاتورة: 2026-10-02
الفجوة المعتادة: 3.5 يوماً · يشتري شهرياً: 8,750 $

2. ABC Trading
الغياب: 6 أيام · آخر فاتورة: 2026-10-08
الفجوة المعتادة: يومان · يشتري شهرياً: 3,421 $
```

بلاغ «البيانات قديمة» (المفتاح `CUSTOMER_INACTIVE_5D:stale:<اليوم>` كما هو):

```
⚠️ فحص غياب الزبائن المهمين لم يُنفَّذ اليوم
السبب: تقرير الفواتير عمره 135 دقيقة (الحد 90 دقيقة)
لا تنبيهات حتى تتحدّث المزامنة.
```

## الفحوص والمعاينة

- `scripts/check-telegram-format.mjs`: العربية وRLM، الأرقام الإنجليزية، السالب، الأسماء
  المختلطة وأحرف HTML حرفياً، حقن محارف الاتجاه والأسطر، القصّ، التقسيم دون شطر كتلة والترقيم،
  توازن العزل، ثبات الحسابات، تطابق نسخة `_shared`، وغياب `parse_mode`. ومنذ المرحلة A:
  التقريب عند النصف، `money`، `time` بتوقيت دمشق، `severity`، القصّ الآمن، رسالة فحص الصحة،
  و**تنفيذ خطوة workflow فشل الأتمتة فعلياً** بـbash وjq مع `curl` وهمي (لا شبكة) للتحقق من
  الرسالة والمفتاح والنافذة والنص الاحتياطي.
- `scripts/check-stock-alert-priority.mjs`: محدَّث لبنية البطاقة.
- معاينة محلية بلا شبكة ولا إرسال: `node scripts/telegram-alert-samples.mjs [--long|--stale]`.

## النشر (بموافقة عمر وحدها)

**المرحلة A:** دمج إلى main فقط؛ لا هجرة ولا Edge. `health-check.yml` و`alert-on-automation-failure.yml`
يعملان من main مباشرة. نسخة `_shared` تتغيّر في المستودع لكن دالة `stock-priority-alert` المنشورة
لا تتغيّر حتى نشرها التالي؛ حينها يتبدّل عرض القيم السالبة عند النصف فقط (`-3.5 كروز` تُعرض
`-4` لا `-3`) — الحالات والأولويات ومفاتيح منع التكرار مطابقة (اختبار 400 حالة مصطنعة).

**المرحلة B:** لا هجرة. بعد الدمج: نشر `customer-inactivity-alert` من الـMac بالـCLI
(`--no-verify-jwt --use-api`، لا أداة MCP لأنها تكسر `\u2028` في `CONTROL_RE`)؛ حتى ذلك الحين تبقى
الرسالة المنشورة بالتنسيق القديم. لا إعادة إرسال بعد النشر: مفاتيح الرسائل وحدود الأجزاء لم تتغيّر،
ومن نُبِّه عنه محفوظ في `customer_inactivity_alerts`. الدالة `customer-credit-snapshot` تحمّل المحرك
نفسه لكنها لا تبني هذه الرسالة، فلا يلزم إعادة نشرها لهذا التغيير.

**المرحلة الأولى (تنبيه النفاد):**

لا هجرة. بعد الدمج: نشر الدالة `stock-priority-alert` (تحمل `_shared/telegram-format.js`).
حتى ذلك الحين تبقى الدالة المنشورة على التنسيق القديم. بصمة منع التكرار لم تتغيّر، لكن عدد
الأجزاء قد يتغيّر لنفس المجموعة (البطاقة أطول من السطر) فيُعاد إرسالها مرة واحدة بعد النشر.
