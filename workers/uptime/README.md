# ozk-uptime — مراقبة الموقع (Cloudflare Worker)

مراقب مستقل عن GitHub Actions لموقع `https://ozktobacco.com/` (GitHub Pages). منشور بوضع الظل (`DRY_RUN=1`) منذ 2026-10-13؛ أي تغيير في النشر أو التفعيل يحتاج موافقة صريحة من المالك.

## ما يفعله
- Cron `*/5 * * * *` (UTC). كل تشغيل يفحص: الموقع (HTTP 200 + النص `OZK TOBACCO`، مهلة 10 ث) والنشرة `price-list-usd.html` (200 فقط).
- الموقع هدف **حرج** (قابل للتنبيه مستقبلاً)؛ النشرة هدف متوسط **تسجيل فقط**.
- آلة حالة لكل هدف: `UP → SUSPECT → DOWN → RECOVERING → UP`.
  - تأكيد العطل: 3 إخفاقات من آخر 4 فحوص (≈15 دقيقة). فشل أو فشلان لا ينتجان شيئاً.
  - التعافي: نجاحان متتاليان. فشل أثناء التعافي يعيد **نفس** الحادثة إلى DOWN (لا حادثة جديدة).
  - تذكيرات للعطل المستمر عند 1 و6 و24 ساعة، مرة لكل عتبة.
- فشل الاتصال يُسجَّل دائماً `ok:false` بسبب صريح (`http-503` / `marker-missing` / `timeout` / `network-error:<Name>`) ولا يُعدّ نجاحاً أبداً.

## الأمان
- `DRY_RUN` مفعّل افتراضياً (أي قيمة غير `"0"`): **لا طلب صادر إلا فحصي `ozktobacco.com`**، والأحداث تُسجَّل بحالة `dry-run` فقط.
- `DRY_RUN="0"` يرسل الأحداث ونبض الحياة إلى Supabase عبر `src/ingest.mjs` فقط، وبشرط إعداد كامل؛ وإلا يُحفظ الحدث معلّقاً ويظهر خطأ `ingest failed (not-configured)`:
  - `SUPABASE_URL` (`https://<ref>.supabase.co` فقط) و`SUPABASE_PUBLISHABLE_KEY` (المفتاح العام، دور anon — ليس سراً).
  - `UPTIME_HMAC_SECRET` (سرّ Worker عبر `wrangler secret put`، ≥ 32 حرفاً) — يوقّع النص الحرفي للطلب بـHMAC-SHA256.
- **لا Telegram ولا service_role في الـWorker.** الخادم (`public.uptime_ingest` في `supabase/proposed/14-uptime-ingest.sql`) يتحقق من التوقيع والنافذة الزمنية (±300 ث) وnonce لمرة واحدة، ثم يقرر وحده الإدخال إلى طابور Telegram القائم، في معاملة واحدة مع تسجيل `event_id`.
- النشرة تسجيل فقط بقرار الخادم (لا يثق بحقل من العميل).
- `wrangler.toml` بلا `account_id` ولا routes ولا أسرار، ولا workflow في المستودع ينشر إلى Cloudflare؛ يفرض ذلك `test/guardrails.test.mjs` (Supabase والسرّ محصوران في `ingest.mjs`، ونقطة صادرة واحدة).

## التسليم (at-least-once مع إقرار صريح)
- الحدث الجديد يدخل `state.pending`، ولا يخرج منها إلا بإقرار صريح من الخادم لمعرّفه (`notified`/`recorded`/`suppressed:*`/`duplicate`). الرد غير 2xx أو المهلة (10 ث) أو انقطاع الشبكة أو رد بلا `ok:true` = فشل ⇒ يبقى معلّقاً ويُعاد في التشغيل التالي.
- الإرسال قبل الحفظ، والحفظ كتابة KV واحدة لكل تشغيل: فشل الحفظ يُبقي الحالة القديمة فتتكرر الانتقالات **بالمعرّفات نفسها** والخادم يرجع `duplicate`.
- `EVENTS_KEEP=20` يقص سجل التشخيص فقط؛ المعلّق لا يطاله القص. حد أمان `PENDING_MAX=100` يُسقط الأقدم غير القابل للتنبيه أولاً مع خطأ `pending-overflow` ظاهر.
- يُرسل طلب في كل تشغيل حتى بلا أحداث: هذا نبض الحياة الذي يراقبه الخادم (`watch_uptime_heartbeat`، توقف > 20 دقيقة ⇒ تنبيه واحد، ثم رسالة تعافٍ واحدة).
- حادثة واحدة لكل انقطاع على الخادم: معرّف حادثة جديد لهدف له حادثة مفتوحة (ضياع حالة KV أو قراءة قديمة) يُسجَّل اسماً بديلاً بلا تنبيه ثانٍ.

## التخزين والاتساق — حدود صريحة
الحالة في مفتاح KV واحد `state:v1` (كتابة واحدة لكل تشغيل ≈ 288/يوم، تحت حد 1000).

> **منع التكرار ليس مضموناً بالكامل باستخدام Workers KV وحده.** KV نهائي الاتساق (eventually consistent): قراءة قد ترجع قيمة قديمة حتى ~60 ثانية، ولا توجد معاملات ولا قفل. لذلك الضمان هنا «أفضل جهد» مبني على:
> 1. **معرّفات أحداث حتمية** (`<target>:<slot>:down|recovered|reminder:<label>`): تشغيلان يقرآن حالة قديمة يُنتجان نفس المعرّف، و**يزيل المستلم التكرار بالمعرّف** (`event_id` مفتاح أساسي في `private.uptime_events`).
> 2. حارس `scheduledTime <= lastRunAt` يتجاهل التشغيل المكرر أو القديم.
> 3. التسليم **قبل** الحفظ (at-least-once): فشل الحفظ يعني إعادة توليد نفس المعرّفات لا ضياع حدث.

حالات الفشل (كلها مختبرة):

| الحالة | السلوك |
|---|---|
| تشغيلان Cron متداخلان | قد يُنتج كلاهما نفس الحدث بنفس المعرّف؛ آخر كتابة تفوز. المستلم يزيل التكرار. وإن اختلف فحصهما أثناء التعافي (أحدهما يرسل `recovered` والآخر يبقى DOWN)، فالخادم لا يُغلق ولا يرسل تعافياً حتى يؤكده تشغيل أحدث تماماً (انظر «التعافي على مرحلتين» أدناه). |
| فشل قراءة KV | لا حكم ولا كتابة (لا نكتب فوق حالة سليمة)؛ يُرمى خطأ ظاهر في سجلات Cloudflare. |
| فشل كتابة KV | 3 محاولات ثم خطأ ظاهر؛ يعاد توليد نفس الأحداث في التشغيل التالي. |
| فقدان الحالة أو تلفها | تبدأ حالة جديدة (`stateLost:true`). أثناء عطل قائم قد يولّد الـWorker معرّف حادثة جديداً، والخادم يضمّه للحادثة المفتوحة بلا تنبيه ثانٍ. |
| قراءة قديمة | قد يتأخر تأكيد عطل/تعافٍ دورة أو دورتين؛ لا يُنتج معرّفاً مختلفاً للحادثة نفسها. |

### التعافي: اعتراض الشقيق وتأكيد على دورتين (الخادم)
KV بلا compare-and-swap، فلا يستطيع الـWorker وحده منع تشغيلين متداخلين لنفس الدقيقة من قرارين متعارضين. لذلك الإغلاق قرار الخادم المسلسَل:
- حدث `recovered` (أو نبض بحالة UP لحادثة مفتوحة بعد ضياع KV) يُسجَّل **تعافياً معلّقاً** فقط: لا إغلاق ولا رسالة.
- أول دورة أحدث تقول UP تصبح **مرشّحة**، ودورة أحدث منها تقول UP **تؤكد**: إغلاق ذرّي (`closed_at` = وقت التعافي الفعلي) ورسالة تعافٍ واحدة بمفتاح فريد لكل إغلاق.
- **اعتراض الشقيق:** أي تشغيل يقول DOWN/RECOVERING بعد التعافي يُلغيه بأي ترتيب وصول، حتى شقيق لنفس الدقيقة وصل بعد UP أو طلب متأخر. الحادثة نفسها تستمر بمعرّفها وتذكيراتها. SUSPECT لا يحسم.
- **شبكة أمان:** DOWN/RECOVERING والخادم بلا حادثة مفتوحة للهدف يعني أنه أغلق ما يحمله الـWorker ⇒ يعيد فتح آخر حادثة برسالة «⚠️ تصحيح»، فتستمر التذكيرات.
- الكلفة: رسالة التعافي بعد دورتين من إشارته (~10 دقائق).
- **انقطاع ثانٍ مستقل:** يعدّ الـWorker دورات الفحص الفعلية التي انتهت بحالة UP منذ آخر تعافٍ (`upTicks`، كل دورة مرة واحدة: التشغيل المكرر أو الأقدم يُتجاهل)، ويرسل العدد مع `down` التالي. إن وصل `down B` بعد `recovered A` معلّق و`upTicks ≥ 2` (نفس شرط التأكيد الحي: مرشّحة ثم مؤكِّدة) تُختم A عند وقت تعافيها برسالتها ويُفتح B بتنبيه مستقل؛ وإلا (تأرجح، أو سباق رأى فيه تشغيل الموقع شغالاً وآخر واقفاً) يبقى انقطاعاً واحداً بلا ✅ وتستمر تذكيراته. فالطابور بعد تعذّر Supabase يعطي نفس نتيجة المسار الحي (مختبر: تعافٍ 5/10/15/20/25 دقيقة، مع تكرار Cron وتأخره).

| الحالة | الضمان |
|---|---|
| تشغيلان متزامنان في أي دورة، بأي ترتيب وصول وأي فائز في KV | **بالكود**: لا إغلاق ولا تعافٍ كاذب (الشقيق المعترض يصل خلال ثوانٍ، قبل الدورة التالية بكثير). |
| نبضة قديمة بعد أحدث | **بالكود**: UP القديم لا يرشّح ولا يؤكد؛ DOWN القديم يعترض (يؤخر فقط). |
| قراءة KV متأخرة (> 5 دقائق) في تشغيل وحيد | **بالكود**: كتابة ذلك التشغيل تصبح الحالة الفعلية، فلا تناقض. |
| شقيق معترض **فشل طلبه** إلى Supabase وكسب KV، **و**قراءة KV متأخرة > 10 دقائق في دورة التأكيد، **و**تشغيل مكرر فيها | **يعتمد على KV**: رسالة تعافٍ كاذبة ممكنة، تتبعها رسالة تصحيح في الطلب نفسه أو الدورة التالية، والتذكيرات لا تتوقف (مختبر). احتمال ضئيل جداً: ثلاثة شذوذات مستقلة معاً. |

للضمان الأقوى لاحقاً: استبدال واجهة التخزين بـ Durable Object (تسلسل صارم) أو D1؛ الواجهة `get/put` معزولة لهذا الغرض.

## الاختبارات (محلية بالكامل)
```
node --test workers/uptime/test/*.test.mjs
```
- الشبكة والتخزين محاكاة؛ لا اتصال بالإنتاج ولا إشعارات.
- محاكاة Wrangler اختيارية، محلية فقط (`--local`، بلا remote bindings ولا تسجيل دخول):
  `cd workers/uptime && npx wrangler dev --local --test-scheduled` ثم
  `curl "http://127.0.0.1:8787/cdn-cgi/handler/scheduled?cron=*/5+*+*+*+*"`
  ولا يكفي رمز HTTP 200 للمعالج: افحص سطر السجل (`ok`/`detail`/`saved`).
- ملف الدخول `src/index.mjs` يصدّر المعالج فقط (قيد workerd)؛ المنطق في `core.mjs`.
- على Windows مع `core.autocrlf=true` يفشل `scripts/check.mjs` محلياً (نافذة regex بطول 700 حرف تتأثر بـ CRLF) ويمرّ على LF/CI؛ لا علاقة له بهذا المجلد.

## خطة التفعيل (بموافقة المالك لكل مرحلة)
1. ✅ الظل: نشر بـ `DRY_RUN=1` مع KV (2026-10-13).
2. كود فقط (هذه المرحلة): `ingest.mjs` + `proposed/14` + الاختبارات. لا نشر ولا تطبيق.
3. تطبيق `proposed/14` على الإنتاج: خاملة (بلا سرّ `uptime_ingest_hmac` ترفض كل طلب، والإرسال والمراقب مقفلان).
4. ظل مع Supabase: سرّ في `app_secrets` وسرّ Worker و`DRY_RUN=0` مع `notify_enabled=false` ⇒ نبض وتسجيل بلا رسائل، ~24 ساعة.
5. اختبار مضبوط برسالة واحدة، ثم `notify_enabled=true` وجدولة `watch_uptime_heartbeat` كل 5 دقائق. حادثة الموقع التي فُتحت في الظل وما زالت مفتوحة يُرسل تنبيهها مع أول نبض بعد التفعيل (مرة واحدة)، ثم تذكيراتها وتعافيها كالمعتاد.
   في `DRY_RUN=1` يبقى المعلّق الحي محفوظاً، وتعافي أو تذكير الحادثة المعلّقة نفسها (بمعرّفها) يلحق بها ليُرسلا معاً عند العودة؛ انقطاع جديد كامل في الظل يبقى تسجيلاً فقط. وإن فُعّل الإرسال والهدف ما زال واقفاً بانقطاع لم يصل الخادمَ، يُعاد حدث down بمعرّفه ووقته الأصليين (التكرار يرجع duplicate)، فتُرسل تذكيراته وتعافيه.
   كل نبض يحمل حالة كل هدف (`targets`)، فإن قال الـWorker إن الموقع UP والخادم عنده حادثة مفتوحة (تعافٍ ضاع مع حالة KV) تُغلق (بعد تأكيد التشغيل التالي) برسالة تعافٍ إن كان أُرسل تنبيهها، كي لا يُكتم الانقطاع التالي.

التراجع: `DRY_RUN=1` (لا طلبات لـSupabase إطلاقاً)، أو `notify_enabled=false` (تسجيل فقط)، أو حذف السرّ (رفض كل طلب، والحدث يبقى معلّقاً عند الـWorker بلا ضياع)، ثم `14-uptime-ingest-rollback.sql`. حذف الـcron أو `wrangler delete` يبقيان متاحين.
