# ozk-uptime — مراقبة الموقع (Cloudflare Worker) — المرحلة 1: DRY_RUN

مراقب مستقل عن GitHub Actions لموقع `https://ozktobacco.com/` (GitHub Pages). **غير منشور**: هذا الدليل وصف للكود فقط؛ النشر والتفعيل يحتاجان موافقة صريحة من المالك.

## ما يفعله
- Cron `*/5 * * * *` (UTC). كل تشغيل يفحص: الموقع (HTTP 200 + النص `OZK TOBACCO`، مهلة 10 ث) والنشرة `price-list-usd.html` (200 فقط).
- الموقع هدف **حرج** (قابل للتنبيه مستقبلاً)؛ النشرة هدف متوسط **تسجيل فقط**.
- آلة حالة لكل هدف: `UP → SUSPECT → DOWN → RECOVERING → UP`.
  - تأكيد العطل: 3 إخفاقات من آخر 4 فحوص (≈15 دقيقة). فشل أو فشلان لا ينتجان شيئاً.
  - التعافي: نجاحان متتاليان. فشل أثناء التعافي يعيد **نفس** الحادثة إلى DOWN (لا حادثة جديدة).
  - تذكيرات للعطل المستمر عند 1 و6 و24 ساعة، مرة لكل عتبة.
- فشل الاتصال يُسجَّل دائماً `ok:false` بسبب صريح (`http-503` / `marker-missing` / `timeout` / `network-error:<Name>`) ولا يُعدّ نجاحاً أبداً.

## الأمان (المرحلة 1)
- `DRY_RUN` مفعّل افتراضياً (أي قيمة غير `"0"`). **لا يوجد في الكود أي مرسِل**: لا Telegram ولا Supabase ولا service_role ولا أسرار ولا Webhook. الطلبات الصادرة الوحيدة هي فحصا `ozktobacco.com`.
- `DRY_RUN=0` **لا يرسل شيئاً حالياً**: تبقى الأحداث بحالة `pending` في السجل فقط. التنبيه الفعلي مرحلة منفصلة لاحقة بموافقة المالك.
- `wrangler.toml` بلا `account_id` ولا routes ولا `workers_dev` ولا أسرار؛ ربط KV معطّل (تعليق + معرّف placeholder) كي لا يُنشر بالخطأ.
- لا workflow في المستودع ينشر إلى Cloudflare، ويفرض ذلك `test/guardrails.test.mjs`.

## التخزين والاتساق — حدود صريحة
الحالة في مفتاح KV واحد `state:v1` (كتابة واحدة لكل تشغيل ≈ 288/يوم، تحت حد 1000).

> **منع التكرار ليس مضموناً بالكامل باستخدام Workers KV وحده.** KV نهائي الاتساق (eventually consistent): قراءة قد ترجع قيمة قديمة حتى ~60 ثانية، ولا توجد معاملات ولا قفل. لذلك الضمان هنا «أفضل جهد» مبني على:
> 1. **معرّفات أحداث حتمية** (`<target>:<slot>:down|recovered|reminder:<label>`): تشغيلان يقرآن حالة قديمة يُنتجان نفس المعرّف، فيجب أن **يزيل المستلم التكرار بالمعرّف** (مثلاً `p_dedupe_key` في Telegram عند ربطه لاحقاً).
> 2. حارس `scheduledTime <= lastRunAt` يتجاهل التشغيل المكرر أو القديم.
> 3. التسليم **قبل** الحفظ (at-least-once): فشل الحفظ يعني إعادة توليد نفس المعرّفات لا ضياع حدث.

حالات الفشل (كلها مختبرة):

| الحالة | السلوك |
|---|---|
| تشغيلان Cron متداخلان | قد يُنتج كلاهما نفس الحدث بنفس المعرّف؛ آخر كتابة تفوز. المستلم يزيل التكرار. |
| فشل قراءة KV | لا حكم ولا كتابة (لا نكتب فوق حالة سليمة)؛ يُرمى خطأ ظاهر في سجلات Cloudflare. |
| فشل كتابة KV | 3 محاولات ثم خطأ ظاهر؛ يعاد توليد نفس الأحداث في التشغيل التالي. |
| فقدان الحالة أو تلفها | تبدأ حالة جديدة (`stateLost:true`). أثناء عطل قائم قد تظهر **حادثة جديدة واحدة** (حدّ معروف). |
| قراءة قديمة | قد يتأخر تأكيد عطل/تعافٍ دورة أو دورتين؛ لا يُنتج معرّفاً مختلفاً للحادثة نفسها. |

للضمان الأقوى لاحقاً: استبدال واجهة التخزين بـ Durable Object (تسلسل صارم) أو D1؛ الواجهة `get/put` معزولة لهذا الغرض.

## الاختبارات (محلية بالكامل)
```
node --test workers/uptime/test/*.test.mjs
```
- الشبكة والتخزين محاكاة؛ لا اتصال بالإنتاج ولا إشعارات.
- محاكاة Wrangler اختيارية، محلية فقط (`--local`، بلا remote bindings ولا تسجيل دخول):
  `cd workers/uptime && npx wrangler dev --local --test-scheduled` ثم
  `curl "http://127.0.0.1:8787/cdn-cgi/handler/scheduled?cron=*/5+*+*+*+*"`
  ولا يكفي رمز HTTP 200 للمعالج: افحص سطر السجل (`ok`/`detail`/`saved`).
- ملف الدخول `src/index.mjs` يصدّر المعالج فقط (قيد workerd)؛ المنطق في `core.mjs`.
- على Windows مع `core.autocrlf=true` يفشل `scripts/check.mjs` محلياً (نافذة regex بطول 700 حرف تتأثر بـ CRLF) ويمرّ على LF/CI؛ لا علاقة له بهذا المجلد.

## خطة التفعيل (لاحقاً، بموافقة المالك لكل مرحلة)
1. الظل: نشر بـ `DRY_RUN=1` مع KV، مراقبة السجلات ~24 ساعة.
2. اختبار مضبوط بموافقة صريحة.
3. التنبيه: مرسِل منفصل؛ بعد SQL 13 يلزم مفتاح dedupe يبدأ بـ `health-site-down` ليبقى فورياً.

التراجع: حذف الـcron أو إعادة `DRY_RUN=1` أو `wrangler delete`.
